Architecture Document

ProofPulse

A cross-chain Proof of Reserve verification system for Wrapped Bitcoin. Reads real-time reserve data from the Bitcoin blockchain and Ethereum, computes collateral health independently, and publishes a verifiable data feed onchain through Chainlink CRE.

Runtime Chainlink CRE (TypeScript SDK)
Target Asset WBTC (Wrapped Bitcoin)
Chains Bitcoin · Ethereum · Sepolia
Data Sources 5 real, public, verifiable
01 — System Overview

Cross-Chain Reserve Verification

ProofPulse operates as an independent reserve auditor. It bridges two separate blockchain networks — reading token supply from Ethereum and reserve balances from Bitcoin — then publishes a computed collateral ratio onchain as a consumable data feed for downstream DeFi protocols.

The system runs as a single CRE workflow with three registered handlers, each serving a different trigger pattern. All external data is fetched through CRE's decentralized node execution with Byzantine Fault Tolerant consensus, ensuring no single node can fabricate reserve data.

Handler 1  CRON
PoR Data Feed Update
Scheduled hourly. Reads supply + reserves from two chains, fetches market price, compares against existing Chainlink feed, publishes aggregate PoR onchain.
1 EVMClient → WBTC.totalSupply()
2 EVMClient → AggregatorV3.latestRoundData()
3 HTTPClient → Blockstream (BTC balances)
4 HTTPClient → CoinGecko (BTC/USD)
5 runtime.report() → writeReport()
Handler 2  LOG
AI Anomaly Detection
Event-driven. Fires on AuditRequested emission. Reads historical state, re-fetches BTC reserves, queries Gemini LLM for anomaly analysis, writes risk score.
1 EVMClient → getLatestReserve()
2 HTTPClient → Blockstream (fresh read)
3 HTTPClient → Gemini LLM (risk analysis)
4 runtime.report() → writeReport()
Handler 3  HTTP
On-Demand PoR Query
API-triggered. Allows external protocols (lending, vaults, bridges) to request a fresh PoR computation before accepting WBTC as collateral. Delegates to Handler 1 logic.
All handlers write to a single consumer contract via CRE Forwarder → onReport()

Collateral Ratio Computation

Core Formula
btcReserveSats = Σ (funded_txo_sum − spent_txo_sum) for each custody address
wbtcSupplySats = WBTC.totalSupply()  // WBTC uses 8 decimals = satoshis
collateralRatioBps = (btcReserveSats × 10000) / wbtcSupplySats
// 10000 bps = 100% fully backed
// > 10000 = overcollateralized, < 10000 = undercollateralized
03 — CRE Execution Model

Runtime & Consensus Architecture

The workflow leverages CRE's dual execution model. Onchain reads and writes execute in DON Mode (consensus-guaranteed by default). External HTTP calls execute in Node Mode, where each DON node fetches independently and results are aggregated through a specified consensus algorithm.

DON Mode (Runtime)

Used for operations with built-in BFT guarantees. The DON handles consensus automatically.

evmClient.callContract(runtime, {...}) READ
runtime.report({...}) SIGN
evmClient.writeReport(runtime, {...}) WRITE
runtime.getSecret({...}) SECRET

Node Mode (NodeRuntime)

Used for external API calls. Each node executes independently. Requires explicit consensus aggregation.

httpClient.sendRequest(nodeRuntime, {...}) HTTP

Wrapped in runtime.runInNodeMode(fn, aggregation)() with consensusIdenticalAggregation — all nodes must return the same result for the value to be accepted.

Onchain Write Path

CRE uses a two-step cryptographic write pattern. The workflow first generates a signed report, then submits it through the Forwarder contract which validates DON signatures before delivering data to the consumer.

Write Sequence
// Step 1: ABI-encode the payload
callData = encodeFunctionData({ abi, functionName, args })
// Step 2: Generate cryptographically signed report
report = runtime.report({ encodedPayload: hexToBase64(callData), ... }).result()
// Step 3: Submit to Forwarder → validates signatures → calls onReport()
tx = evmClient.writeReport(runtime, { receiver, report }).result()
04 — Smart Contract

Consumer Contract Design

A single contract serves as both the PoR data feed and the risk registry. It implements IReceiver to accept reports from the CRE Forwarder and uses function selector routing in onReport() to dispatch to internal handlers.

WBTCProofOfReserve.sol IReceiver
State — Reserve Data Feed
latestReserve → { btcReserveSats, wbtcSupplySats, collateralRatioBps, btcUsdPriceCents, chainlinkReserveSats, timestamp }
reserveHistory[] — append-only log of all PoR snapshots
latestRisk → { score: uint8, recommendation: string, timestamp }
Forwarder-Only (via onReport)
updateReserve(btcSats, wbtcSats, ratioBps, priceCents, clSats, ts) FORWARDER
updateRisk(score, recommendation, timestamp) FORWARDER
Public Interface (DeFi Consumable)
isHealthy() → bool PUBLIC
getLatestReserve() → ReserveData VIEW
getLatestRisk() → (uint8, string) VIEW
getReserveValueUsd() → uint256 VIEW
requestAudit(auditId) — emits AuditRequested event → triggers Handler 2 PUBLIC
Events
ReserveUpdated UndercollateralizedAlert ChainlinkDivergenceAlert RiskUpdated AuditRequested

Selector Routing Pattern

The onReport() function extracts the first 4 bytes of the report payload as a function selector and routes to the corresponding internal handler. This allows a single contract to serve multiple CRE workflow handlers without separate receiver deployments.

08 — DeFi Integration Surface

Downstream Protocol Consumption

The contract exposes a minimal, gas-efficient interface designed for integration into lending protocols, DEX circuits, vault strategies, and bridge validators that need to verify WBTC backing before accepting it as collateral.

Integration Example — Lending Protocol
// Before accepting WBTC as collateral:
require(
  IWBTCProofOfReserve(porAddress).isHealthy(),
  "WBTC reserves insufficient"
);
// For more granular checks:
(uint256 btcSats, , uint256 ratioBps, , , uint256 ts) =
  IWBTCProofOfReserve(porAddress).getLatestReserve();
require(ratioBps >= 9900, "Ratio below 99%");
require(block.timestamp - ts < 7200, "Data stale");
